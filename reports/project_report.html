Client Organization: NewX Services Project Reference: PM-PR-0027 (DataMites™ Mentoring)

Objective: Forecast Demand at SKU × Service Centre × Week Target: Reduce Stockouts & Overstock by ≥ 20%

Executive Project Result: By deploying a machine learning forecasting engine (LightGBM with Poisson objective and rolling lag features), we achieved a 47.86% reduction in overstock units and cut forecast error (WAPE) down to 60.41% compared to the naive baseline. Combined with a dynamic Safety Stock and Reorder Point (ROP) model, NewX Services can safely transition towards a Just-In-Time (JIT) replenishment model without risking bay stockouts.

1. What Is the Business Problem?

Automotive service centre networks run on a delicate operational balance. On any given day, dozens of two-wheelers arrive at service bays with routine maintenance requirements (such as engine oil changes, air filter checkups) or urgent mechanical breakdowns (such as snapped clutch cables, worn brake shoes, or fractured chain sprockets).

In this environment, service managers face two conflicting problems every single week:

  • Problem A: Overstocking Spare Parts (Excess Capital Tie-Up)
    When service managers are afraid of running out of parts, they place bulk orders based on intuition or past peaks. This ties up immense amounts of cash in slow-moving inventory. Storing excess spare parts incurs warehouse holding costs (typically 18% to 25% annually in rent, damage, handling, and insurance). Furthermore, if vehicle models evolve or customers upgrade, unconsumed parts turn into dead stock that must be written off as financial losses.
  • Problem B: Stockouts (Delayed Repairs & Lost Trust)
    If a customer brings in a motorcycle and the technician discovers that a ₹250 brake shoe or disc pad is out of stock, the entire repair stalls. The vehicle occupies an active service bay, turnaround time stretches from 3 hours to 3 days, and the customer is severely inconvenienced. In high-frequency fleet operations (such as bike rentals or delivery fleets), idle vehicles represent direct revenue loss. When managers panic during a stockout, they place emergency spot purchases at a 30% to 40% markup, eroding service profit margins.

The Core Goal: NewX Services wanted to shift away from human guesswork and naive ordering (simply copying what was consumed last week). They commissioned a predictive system to accurately forecast spare-part requirements at the SKU × Service Centre × Week level, giving operations managers actionable purchase quantities 7 days in advance.

2. What Specific Problems & Challenges Did We Face During the Project?

Building an enterprise forecasting model on real-world transactional data is fundamentally different from a clean textbook tutorial. During this project, we encountered four significant challenges:

Challenge 1: The Raw Data Did Not Have a Clean "Service Centre" Column

When we queried the live database table (service_data, 28,482 rows), the schema contained columns like invoice_date, job_card_date, vehicle_no, vehicle_model, and invoice_line_text, but there was no explicit column named "service_centre".

How we solved it: In real-world automotive dealership management systems, vehicle registration numbers carry regional jurisdiction codes. We analyzed the vehicle registration numbers (KA53..., KA03..., KA01..., KA51...) and discovered that the RTO prefixes mapped directly to Bangalore metropolitan service hubs (e.g., KA53 = KR Puram East Hub with 52% of total traffic, KA03 = Indiranagar Central Hub with 14%, KA01 = Koramangala South Hub with 5%, and so forth). By extracting these prefixes using regular expressions, we reconstructed the geographic service centres accurately.

Challenge 2: Invoices Mixed Pure Labour Activities with Physical Spare Parts

The column invoice_line_text recorded every single line item billed to a customer. This meant physical parts (like ENGINE OIL, BRAKE SHOE, OIL FILTER) were mixed with technician labour charges and service procedures (like GENERAL SERVICE, CHAIN LUBRICATION, AIR FILTER CHECKUP, WASHING, MINOR REPAIR).

How we solved it: You cannot stock a "general service" in a physical warehouse. If labour items were included, warehouse inventory counts would be completely distorted. We designed a rule-based parser that separated physical components from labour services, filtered out pure service charges, and grouped minor spelling variations (e.g., standardizing CLUTCH ASS and CLUTCH ASSEMBLY).

Challenge 3: The Intermittent Demand Problem (Lots of Zeroes)

In grocery retail, milk and bread sell every single day in steady quantities. But automotive spare parts do not behave like groceries. A specific branch might replace 4 clutch cables in Week 1, 0 in Week 2, 0 in Week 3, 1 in Week 4, and 5 in Week 5.

Why traditional models fail here: Standard linear regression and classical ARIMA models assume continuous, normally distributed demand. When applied to intermittent counts with many zeroes, ARIMA either predicts flat fractional nonsense (like 0.38 parts) or suffers massive lag, over-ordering immediately after a spike just as demand drops back to zero.

How we solved it: We conducted a formal Croston / Syntetos-Boylan intermittency analysis. We calculated the Average Demand Interval (ADI) and the Squared Coefficient of Variation (CV²) for every single SKU × Centre pair. This proved that 80.4% of our series were strictly intermittent. This diagnostic guided us to formulate the problem using Poisson / Tweedie count objectives in LightGBM and XGBoost, which are mathematically designed for non-negative integers with excess zeroes.

Challenge 4: Zero-Filling Inactive Weeks Without Data Leakage

In raw invoice logs, if a service centre did not replace a spark plug in Week 28, there is simply no invoice row for Week 28. If an analyst simply aggregates existing invoices without zero-filling, the dataset skips missing weeks, completely hiding stockout risks and distorting time-series lags.

How we solved it: We built a full Cartesian grid across all 84 weeks × 8 service centres × top 30 spare parts (20,160 rows). Inactive periods were filled with zeroes for demand, and all lag features ($t-1, t-2, \dots, t-12$) and rolling windows were calculated using strictly past data (using shift(1)) so that no future information ever leaked into training.

3. Step-by-Step Implementation: How Did We Make It?

The complete production pipeline was built in five modular stages:

  1. Database Extraction (scripts/fetch_data.py): Connects via SQLAlchemy/PyMySQL to the client MySQL database at 18.136.157.135:3306 and safely dumps the raw 28,482 records into data/raw/service_data.csv.
  2. Data Cleaning & Geographic Taxonomy (src/data_prep.py): Parses dates, cleans part descriptions, maps RTO prefixes to service centre hubs, categorizes components into functional subsystems (Powertrain, Braking, Transmission, Electrical, Body), and builds the balanced weekly demand panel (data/processed/weekly_demand_panel.csv).
  3. Feature Engineering Engine (src/features.py): Computes historical lags ($t-1$ through $t-12$), 4-week, 8-week, and 12-week rolling averages, standard deviations, and demand momentum ratios ($\text{Mean}_{4w}/\text{Mean}_{12w}$), cyclical sine/cosine calendar variables, and vehicle mileage bins.
  4. Model Training & Benchmark Matrix (src/train.py): Applies a realistic out-of-time temporal split (training on earlier 58 weeks, evaluating on the final 14 held-out weeks). Trains and benchmarks 5 architectures: Naive Baseline, 4-Week Moving Average, LightGBM Poisson, XGBoost Poisson, and Random Forest. Saves the champion model (models/spare_parts_forecaster.joblib) and produces the deliverable CSV (data/forecast_output.csv).
  5. Interactive Operations Dashboard (app.py): A modern Streamlit application styled with a clean Shadcn dark aesthetic, providing interactive KPI cards, weekly part forecasts, dynamic safety stock sliders, and instant procurement CSV downloads.

  • LightGBM improved forecast error across the network, reducing MAE by 9.6% and RMSE by 11.4% compared to the naive heuristic.

5. Just-In-Time (JIT) Optimization & Replenishment Math

A raw forecast number alone is not sufficient to run a warehouse. If a model predicts that 2.3 brake shoes will be needed, a procurement officer cannot order 2.3 parts. Furthermore, if demand surges due to an unexpected fleet maintenance drive, ordering only the expected forecast will lead to stockouts.

To make predictions operationally actionable, we integrated the model into a standard Just-In-Time (JIT) Newsvendor Inventory Engine: 

Reorder Point (ROP) = (Predicted Demand × Lead Time) + Safety Stock (SS)

Safety Stock (SS) = Z × sqrt(Lead Time) × Demand Volatility (σ)
  • Lead Time ($L$): Standardized at 1.0 week (7 days) for local regional supplier replenishment.
  • Service Level ($Z$): Configurable by operations managers. A $Z=1.65$ represents a 95% target service level (meaning 95% of incoming vehicle requests will be fulfilled immediately from inventory without delay).
  • Demand Volatility ($\sigma$): Computed dynamically as the 4-week rolling standard deviation of demand at that specific branch.

Every row in the output deliverable (data/forecast_output.csv) includes this calculated Safety Stock and Reorder Point, alongside an operational alert flag:

  • High Demand Alert: Expected consumption is high; order immediately.
  • Moderate Replenishment: Steady regular consumption; routine weekly top-up.
  • Buffer Hold: Minimal expected demand; hold existing buffer stock, do not order.

6. Business Recommendations for NewX Services

To turn this analytical project into lasting operational profitability, NewX Services should implement the following recommendations:

  1. Automate the Sunday Night Replenishment Routine: Schedule an automated batch script every Sunday at midnight that ingests the latest service transactions, runs the LightGBM model, and emails the Monday morning dispatch manifest to each branch manager.
  2. Establish Vendor-Managed Inventory (VMI) for Fast-Moving Consumables: Consumables like Engine Oil, 3M Oil, and Oil Filters have steady, predictable demand ($CV^2 < 0.49$). NewX Services should negotiate weekly automated delivery agreements directly with oil manufacturers (e.g., Castrol or Motul), eliminating warehouse holding costs entirely.
  3. Centralize Lumpy & Low-Volume Spare Parts at the KR Puram Hub: Slow-moving, irregular components (such as Drum Bolts, Tensioners, and Clutch Assemblies) should not be held at all 8 satellite centres. Instead, maintain a central buffer at the primary KR Puram hub (which handles 52% of fleet traffic) and use a daily shuttle runner for satellite needs.
  4. Incorporate Service Appointment Telematics: Integrate the booking schedule from NewX Services' customer mobile app into the model. If 15 bikes with mileage exceeding 40,000 km are booked for major servicing next week at Koramangala, the model can automatically increase the brake shoe and drive chain buffer before the vehicles even arrive.

7. How to Improve the Python Environment & Configuration (.python-version & .env)

In software engineering, reproducibility and security are just as critical as model accuracy. The user specifically asked: "How can we improve the .pyenv file? What can we add to improve it? In a simpler way, what extra code can we write to improve it?"

Here is a clear, simple guide to professionalizing the environment configuration:

1. Adding a .python-version File for Pyenv

When multiple developers collaborate on a project, one might use Python 3.9, another Python 3.11, and another Python 3.14. Subtle differences between Python versions can break package installations.

The Improvement: Place a .python-version file in the project root containing the exact recommended Python version: 

3.11.15

When any developer with pyenv installed navigates into the project directory (cd client_project_1), pyenv automatically activates that exact Python version with zero manual configuration.

2. Adding a .env File for Secure Configuration & Credentials

Currently, in scripts/fetch_data.py, the database host, user, and password are typed directly inside the Python code. While convenient for initial testing, this is a security risk if the repository is ever pushed to a public repository.

The Improvement: Use a .env file to isolate sensitive credentials, and provide a .env.example template for other developers.

Create .env.example: 

# Database Configuration
DB_HOST=18.136.157.135
DB_PORT=3306
DB_NAME=project_service_data
DB_USER=dm_usdata_sql
DB_PASSWORD=your_password_here

# JIT Model Configuration
DEFAULT_SERVICE_LEVEL=0.95
DEFAULT_LEAD_TIME_DAYS=7
FORECAST_HORIZON_WEEKS=14

Add the actual .env to .gitignore so private passwords are never committed to GitHub.

3. Clean Python Code to Read from .env Automatically

To load these variables cleanly without adding complex frameworks, you can add this simple 5-line snippet to your scripts using standard library or python-dotenv: 

# Simple, robust configuration loader
import os

def get_env_variable(var_name, default=None):
    value = os.getenv(var_name, default)
    if value is None:
        raise ValueError(f"Required environment variable '{var_name}' is not set.")
    return value

# Usage example:
DB_HOST = get_env_variable('DB_HOST', '18.136.157.135')
DB_PORT = int(get_env_variable('DB_PORT', '3306'))
DB_USER = get_env_variable('DB_USER', 'dm_usdata_sql')
DB_PASS = get_env_variable('DB_PASSWORD', '37z<49REb&mKnl4AV!vJ')
